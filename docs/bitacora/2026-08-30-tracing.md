# 2026-08-30 — Tracing distribuido del sistema de agentes (Idea 7, post-roadmap)

Primera idea después de cerrar el roadmap de 6 (ver `docs/29110/idea7-tracing/` para el detalle formal). Objetivo: dejar de tratar el sistema multi-agente como una caja negra por request — propagar un solo trace_id desde el Diagnostician (o Operator/Watcher/webhook) a través de los 3 servidores MCP y de cada llamada a Ollama, visible como un único árbol de spans en Jaeger.

## Hallazgo que cambió el plan: el SDK de MCP ya trae OpenTelemetry embebido

El plan original suponía tener que instrumentar cada tool a mano — inyectar el contexto de trace en los argumentos de cada llamada, extraerlo del lado del servidor, etc. Investigando el SDK real (`mcp[cli]>=2.1.1`) antes de escribir ese código, se encontró `mcp.server._otel.OpenTelemetryMiddleware`: ya envuelve **cada** `tools/call` en un span (`gen_ai.tool.name`, `gen_ai.operation.name`) y extrae automáticamente el `traceparent` del campo `_meta` de la request. Del lado del servidor, instrumentar fue literalmente configurar el `TracerProvider` — cero cambios a las tools en sí. Del lado del cliente, solo hizo falta inyectar el contexto con `opentelemetry.propagate.inject()` en el `meta` que ya soporta `client.call_tool(..., meta=...)`.

## Infra
Jaeger v2 nuevo en el LXC `observability` (ver `observability/docs/bitacora/2026-08-30-jaeger.md` — incluye el hallazgo de que v1 ya estaba EOL).

## Cambios en este repo
- `tracing.py` (nuevo) — configura el `TracerProvider` global, opcional (no hace nada si `OTEL_EXPORTER_OTLP_ENDPOINT` no está seteado).
- `mcp_tools.py` — `ToolRegistry.call()` envuelve cada llamada en un span `tool_call <name>` e inyecta el contexto en `meta` antes de `client.call_tool()`.
- `diagnostician.py`, `operator.py`, `watcher.py`, `webhook.py` — cada punto de entrada abre un span raíz (`diagnose`, `operate`, `watch.check_once`, `webhook.alertmanager`) — todos son entradas genuinamente nuevas (nadie les propaga contexto desde afuera).
- `agent.py` — la llamada a Ollama (`_chat`) queda como su propio span `ollama.chat`, con las mismas convenciones semánticas `gen_ai.*` que ya usa el middleware del SDK — un solo vocabulario de atributos en todo el trace, no dos inventados por separado. Incluye tokens de entrada/salida cuando Ollama los devuelve.

## Verificado con una consulta real, no un caso trivial

`uv run devops-agent diagnose "cual es el estado del nodo de proxmox, cuantos pods hay en kubernetes, y busca en la bitacora por que se eligio bge-m3"` — dispara los 3 servidores MCP en una sola conversación. Resultado en Jaeger: **un solo trace_id, 24 spans**, árbol completo:

```
diagnose (17.4s)
├── ollama.chat (5.9s)
├── tool_call list_nodes (30ms)      → proxmox-mcp-server: tools/call list_nodes (11ms)
├── tool_call list_k8s_pods (19ms)   → k8s-mcp-server: tools/call list_k8s_pods (17ms)
├── tool_call search_knowledge (838ms) → rag-mcp-server: tools/call search_knowledge (836ms)
│                                          ├── ollama.embed (32ms)
│                                          └── qdrant.query_points (31ms)
└── ollama.chat (8.4s)
```

Confirma dos cosas a la vez: que la propagación de contexto cruza procesos reales (subprocess de cada MCP server, conectado via stdio) correctamente, y que los tiempos son reales y útiles — por ejemplo, que la mayor parte del tiempo de una consulta típica está en el razonamiento del LLM (`ollama.chat`, ~14s de los ~17s totales), no en las tools.
