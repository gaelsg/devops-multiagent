# 2026-08-28 (parte 2) — Idea #2: agente proactivo con notificaciones

## Contexto
Segunda idea del brainstorm post-Fase-4: pasar de "reactivo" (solo responde cuando le preguntas) a "proactivo" (te avisa solo cuando algo cambia). Se decidió no invocar el LLM en cada chequeo rutinario — un watcher determinista compara estado actual vs último conocido, y solo si hay diferencia real se dispara notificación + diagnóstico del LLM.

## Decisiones
- **Canal:** Telegram (bot propio), sobre ntfy — el usuario ya usa Telegram a diario.
- **Intervalo:** 15 minutos, via **systemd --user timer** (no un loop de Python corriendo siempre) — declarativo, se integra con el resto del sistema, se puede inspeccionar con `systemctl`/`journalctl`.
- **Linger habilitado** (`loginctl enable-linger gaelsg`, sin sudo) para que el timer corra aunque no haya sesión de usuario activa — si no, systemd --user se apaga al cerrar sesión y el watcher dejaría de correr.
- **Deteccion:** comparación de estado (`list_nodes` + `list_containers`) contra un JSON local (`state/last_known.json`, gitignored — es estado runtime, no código). Primera corrida sin estado previo = solo guarda línea base, no notifica (evita falsa alarma de "todo acaba de aparecer").
- **Dos notificaciones por cambio:** una cruda inmediata (el hecho, sin esperar al LLM) y una de diagnóstico (invoca al Diagnostician con contexto del cambio + RAG). Diseño defensivo: si el diagnóstico falla, la alerta cruda ya salió — lo crítico no depende de lo opcional.

## Bug real encontrado y corregido: alucinación de nombre de nodo
Al probar con un cambio de estado real (LXC 100 detenido), el diagnóstico crasheó: el modelo llamó `get_resource_status(node='pve', ...)` en vez de `batman01` — alucinó el nombre de nodo "de ejemplo" típico de la documentación de Proxmox, porque el prompt no se lo dejaba explícito. Fix: el prompt ahora incluye el nombre del nodo real y le dice explícitamente que lo use, no que invente otro. Ademas se envolvió la llamada a `diagnose()` en try/except — si falla, la alerta cruda (ya enviada antes) no se pierde, solo se pierde el enriquecimiento.

## Verificado end-to-end (2026-08-28)
- Prueba real: se detuvo LXC 100 (Nextcloud) a proposito (`stop_resource`, con aprobacion), el watcher detecto `running -> stopped` y mando ambas notificaciones (cruda + diagnostico crasheado la primera vez). Corregido el bug, se reinicio el contenedor (`start_resource`), el watcher detecto `stopped -> running` y esta vez **ambas notificaciones llegaron correctamente** confirmado por el usuario en Telegram.
- Timer de systemd instalado y habilitado (`devops-watcher.timer`, cada 15 min desde `%h/projects/devops-multiagent`, unidades versionadas en `systemd/` del repo y symlinkeadas a `~/.config/systemd/user/`). Primera corrida automatica verificada via `journalctl --user -u devops-watcher.service`: 0 cambios, salida limpia.

## Nota operativa
Durante las pruebas, el clasificador de auto-mode de Claude Code bloqueo consistentemente la ejecucion directa de `stop_resource` desde el asistente (si permitio `restart_resource` antes) - el usuario tuvo que correr el stop el mismo desde su terminal. Es una capa de seguridad adicional fuera del propio sistema (Claude Code, no proxmox-mcp-server), no un bug del proyecto.
