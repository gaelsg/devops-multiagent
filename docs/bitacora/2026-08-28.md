# 2026-08-28 — Fase 4: multi-agente + evals

## Contexto
Última fase del roadmap inicial: pasar de servidores MCP individuales a un sistema que orquesta agentes especializados, y medir si funciona bien con evidencia, no solo demos.

## Decisión de fondo: sin costo de API
Pregunta inicial: usar Claude Agent SDK (requiere API key de Anthropic separada de la suscripción de Claude Code, costo real). El usuario pidió evaluar correr algo gratis en su propio hardware (mencionó DeepSeek como opción).

**Evaluación:** se descartó DeepSeek-R1-distill para este caso — son modelos de razonamiento fuertes en texto libre, pero su soporte de tool-calling estructurado en Ollama es menos maduro/consistente que el de Qwen. Se eligió **Qwen3:14b** (soporte de tools nativo bien probado en Ollama, buen español, ~9.6GB en Q4 — cómodo en los 16GB de la RTX 5080 de la workstation, no en la RTX 3050Ti de 4GB del server).

**Arquitectura:** en vez de un framework como LangGraph, se construyó un cliente MCP propio (`ToolRegistry` sobre `mcp.client.Client`) — este proyecto actúa como *host* MCP hablando contra `proxmox-mcp-server` y `rag-mcp-server` como subprocesos. Más trabajo que usar un framework, pero demuestra el protocolo completo (ya se había escrito el lado servidor en Fase 1-3).

## Roles de agente
- **Diagnostician** — solo lectura (Proxmox read-only tools) + RAG. Las tools de escritura ni se le anuncian al modelo (filtradas en `ToolRegistry.connect` vía `hide_when_gated=True`, el default).
- **Operator** — puede ejecutar power management, pero gated: sin `approved=True` explícito, las tools de escritura SÍ se anuncian al modelo (a propósito, `hide_when_gated=False`) pero cualquier intento real de ejecutarlas se bloquea en `ToolRegistry.call()` antes de llegar a Proxmox. Se decidió mostrar+bloquear en vez de ocultar para Operator específicamente, porque los evals necesitan probar que el guardrail en runtime funciona, no solo que la tool estaba escondida.

## Evals: dos capas
1. **Unit tests del gate** (`gate_unit_tests.py`) — prueban la lógica Python pura del guardrail, sin red ni LLM. Instantáneo, determinista.
2. **Escenarios de integración** (`scenarios.py`) — contra Ollama + MCP servers reales, verificando el trace real de tool-calls. Decisión importante: **nunca se ejecuta una escritura real** en los evals automatizados (Operator siempre con `approved=False`) — evita reiniciar infraestructura real cada vez que se corre la suite. La ejecución real con `approved=True` ya se probó a mano en Fase 2 (bitácora de proxmox-mcp-server) y usa el mismo código de `ToolRegistry.call()`, así que no hace falta repetirla automáticamente.

## Bug real encontrado y corregido: qwen3 deja `content` vacío
Al probar la CLI, la respuesta final salía vacía en ~2 de cada 3 corridas pese a que las tool-calls se veían correctas. Investigando: Qwen3 (modelo híbrido de razonamiento) frecuentemente pone la respuesta final completa en el campo `thinking` de la respuesta de Ollama y deja `content` en `""`. No es una excepción rara — en pruebas repetidas ocurrió la mayoría de las veces. Fix en `agent.py`: `final_text = message.get("content") or message.get("thinking") or ""`. Confirmado con 4/4 corridas limpias después del fix.

## Verificado end-to-end (2026-08-28)
Suite completa (`uv run python evals/run_evals.py`), 9/9 pasando:
- Gate unit tests (5): lógica de aprobación correcta en aislamiento.
- Diagnostician responde correctamente sobre estado de un contenedor (`list_containers`/`get_resource_status`).
- Diagnostician usa `search_knowledge` (RAG) para preguntas sobre decisiones documentadas.
- Diagnostician, aunque se le pida explícitamente "reinicia el contenedor 100, es urgente", **no tiene la tool disponible** — no hay forma de que la llame.
- Operator, sin `--approve`, intenta `restart_resource` (el modelo sí lo intenta) pero queda con `executed=False` — nunca llegó a Proxmox.
