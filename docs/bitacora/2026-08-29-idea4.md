# 2026-08-29 — Idea #4: dashboard web para devops-multiagent

## Contexto
Hasta ahora `diagnose`/`operate`/`watch` solo existían como CLI (`devops-agent ...`). El trace de tool-calls se veía completo pero solo al final, después de que el agente terminaba. Objetivo: una interfaz simple que muestre ese trace en vivo, más el historial de auditoría de acciones reales, sin meter un framework de frontend.

## Decisiones tomadas antes de escribir código
Dos preguntas explícitas al usuario antes de empezar, porque afectan el modelo de seguridad:

1. **Bind solo a `127.0.0.1`** (no LAN/Tailscale). El dashboard no tiene login — exponerlo en red hubiera requerido agregar auth básica primero, ya que aunque v1 es solo lectura, es la puerta de entrada a un sistema que sí puede escribir en infra real (Operator, aunque no esté en la UI todavía).
2. **Solo Diagnostician en v1, sin panel de Operator.** Un botón "reiniciar" en un navegador es más fácil de gatillar por error que teclear `devops-agent operate ... --approve` en una terminal. El guardrail real (gate en `ToolRegistry`) seguiría intacto si se agregara Operator después, pero se prefirió no sumar superficie de riesgo todavía.

## Arquitectura
- **FastAPI** sirviendo HTML vía Jinja2 (`src/devops_multiagent/web/app.py` + `web/templates/`), no una API JSON separada — el patrón es "server returns HTML fragments", que es justo lo que htmx espera.
- **Trace en vivo = SSE**, no polling. `run_agent()` en `agent.py` ganó un parámetro opcional `on_event` (callback async invocado después de cada `registry.call()` real) — cambio no invasivo, el CLI y los evals lo siguen llamando sin ese argumento y no cambia nada para ellos.
- El endpoint `/diagnose/stream` corre `diagnose()` en una task de asyncio, empuja cada evento a una `asyncio.Queue`, y un generador async va sacando de la cola y emitiendo `event: tool_call` / `event: final` / `event: close` como SSE. El front usa `htmx-ext-sse` (`hx-ext="sse"`, `sse-connect`, `sse-swap`) para ir agregando cada tool-call al DOM según llega, sin JS propio.
- `sse-close="close"`: sin esto, `EventSource` reintenta conectar automáticamente cuando el server cierra la respuesta (comportamiento estándar del protocolo) — hay que decirle explícitamente al cliente "ya terminamos" con un evento nombrado `close` para que no quede reintentando un stream que ya no vendrá.
- Historial de auditoría: lee directo `proxmox-mcp-server/docs/audit/actions.jsonl` (ruta absoluta hardcodeada, mismo proyecto en la misma máquina) y se re-renderiza cada 30s vía `hx-trigger="load, every 30s"` — sin SSE ahí, no hace falta, es barato regenerar la tabla completa.

## Verificado (2026-08-29)
- `uv run devops-agent serve` levanta en `127.0.0.1:8000`.
- `curl -sN /diagnose/stream?message=...` contra Ollama + proxmox-mcp-server reales: trace de `list_nodes` en vivo seguido de la respuesta final, formato SSE correcto (multilínea con `data:` repetido por línea).
- `/audit` renderiza filas reales del `actions.jsonl` de `proxmox-mcp-server`.
- Suite de evals completa (`evals/run_evals.py`) sigue en 9/9 tras el cambio en `agent.py` — el `on_event` opcional no rompió nada existente.

## Hallazgo colateral: Qdrant no sobrevive un reboot
Al correr los evals se encontró `search_knowledge` fallando — el contenedor `qdrant` (podman) estaba `Exited (143)` desde 34h antes, es decir, no se levantó solo tras el último reinicio del server/workstation. Se resolvió con `podman start qdrant` para esta sesión.
